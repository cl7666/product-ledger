## 二、项目主要功能与技术架构

### 2.1 功能定位

一个"自定义表格 + 标准产品台账"双轨的内网仓库数据管理系统：

1. **自定义表格**：像 Excel 一样自由加字段（文本/多行文本/数字/下拉/日期），支持表头拖拽排序改列宽、分页、全字段搜索、多条件筛选（等于/包含/区间/为空…）、排序、批量删除。
2. **产品台账**：13 个固定字段，金额 = 单价 × 库存自动计算，库存 ≤ 10 高亮预警，分类/状态/仓库筛选。
3. **双向互通**：表格 → 台账（按编号 upsert 或新增）、台账 → 任意表格（字段映射）。
4. **Excel 能力**：台账式带格式导出（标题/元信息/蓝底表头/斑马纹/冻结/合计行）、导入向导（上传 → 选工作表 → 列映射 → 追加/更新 → 失败明细）。
5. **用户与权限**：JWT 登录、登录失败限流、改密、头像裁剪压缩、admin/member 两级角色、行级"谁录入谁可改"、操作日志（22 类操作，保留 500 条）。
6. **工作台**：产品数、库存金额、数据条数、预警数、最近表格/操作、分类分布。

### 2.2 架构

```
浏览器 (React 18 + AntD 5 + Vite 6)
        │  axios (/api，Bearer token，localStorage)
        ▼
Express 4 (ESM, 单进程)
  ├─ 中间件：compression / 安全响应头 / CORS 收敛 / express.json(10MB) / 统一错误处理
  ├─ 路由：auth · users · tables · ledger · stats(/logs)
  ├─ 领域层：store.js(规范化+校验) · query.js(筛选/排序/分页) · excel.js(ExcelJS)
  ├─ 会话：import-sessions.js(内存 30min TTL)
  └─ 存储：db.js（单文件 JSON + 50ms 合并写 + 原子 rename + 损坏备份）
        │
        ▼
server/data/db.json（users / tables / rows / ledger / logs / meta）
```

- **部署形态**：开发期前后端分端口（API 4399 + Vite 5173 代理 `/api`）；生产期 `web/dist` 由 Express 静态托管，单端口 4399。
- **数据模型**：无关系数据库，采用"扁平集合 + 外键字段"（`tableId` / `ownerId` / `createdBy`），一次读全库进内存，按需过滤，写操作防抖整库落盘。
- **鉴权链**：登录签发 12h JWT（`sub` + `role`）→ 每次请求 `requireAuth` 用 `sub` 回库取最新用户（删除/降权即时生效）→ `requireAdmin` 二次校验。前端 401 拦截器统一清 token 跳登录。

## 五、缺陷与潜在问题清单

> 位置均指当前仓库代码；P1 = 投产前应修，P2 = 尽快修，P3 = 优化项。

### P1-1 表格 upsert 局部映射会清空未映射列（数据丢失）

```347:351:server/src/routes/tables.js
    const input = {};
    for (const [colKey, idx] of pairs) input[colKey] = cells[idx] ?? '';
    const data = normalizeRowData(table, input);
```

`normalizeRowData` 会为**所有**列生成值（未出现在 `input` 的列 → 文本 `''`、数字 `null`），随后 upsert 分支又整对象覆盖：

```387:387:server/src/routes/tables.js
        target.data = { ...target.data, ...data };
```

实测：只映射 `编号 + 名称` 时，原行的 `等级/备注` 变空、`数量` 变 `null`。台账侧因为 `readLedgerPayload` 只处理传入字段而**没有**此问题，两边行为不一致，更容易被误认为"已验证过"。

**建议**：`normalizeRowData` 增加 `{ partial: true }` 或新增 `buildRowPatch(table, mappedInput)`，upsert 时只合并"实际参与映射的列"；合并后再跑一次完整 `validateRow`。

### P1-2 `sync-ledger` 缺少行级权限校验（越权覆盖他人台账）

```509:516:server/src/routes/tables.js
    let target = null;
    if (mode === 'upsert' && code) {
      target = db.ledger.find((l) => String(l.code).toLowerCase() === code.toLowerCase());
    }
    if (target) {
      Object.assign(target, patch, { updatedAt: now(), updatedBy: req.user.id });
      updated += 1;
```

成员在自己建的表格里录一条相同编号的行，即可覆盖管理员录入的台账；而单条 PATCH、Excel 导入都做了 `canEditLedger` 校验（`routes/ledger.js#L18`），此处漏了，README 的权限承诺被绕过。

**建议**：抽出 `canEditLedger(user, entry)` 到 `store.js`，在 `sync-ledger` 更新分支前校验，越权记 `skipped` 并回传原因（与导入的失败明细一致）。

### P1-3 `sync-ledger` 可绕过"产品编号唯一"

`mode` 只判断 `mode === 'upsert'`，任何其他值（`insert` / `merge` / 拼写错误）都走"直接 push"，且新建时不检查编号是否已存在。实测同编号出现 2 条。前端 `SyncLedgerModal` 还主动提供"总是新增"选项。

**建议**：`mode` 白名单（`upsert|insert`），`insert` 分支也做编号唯一校验（重复则该行 skipped），或明确改为"编号加后缀"策略并在 UI 说明。

### P1-4 台账必填字段可被 PATCH 清空

```157:164:server/src/routes/ledger.js
  const payload = readLedgerPayload(req.body || {});
  if (payload.code) {
    const dup = db.ledger.find(...);
    if (dup) throw new HttpError(400, ...);
  }
  Object.assign(entry, payload, { updatedAt: now(), updatedBy: req.user.id });
```

`payload.code` 为空串时跳过唯一性检查，但仍被 `Object.assign` 写入，于是产生"无编号/无名称"的台账记录，后续 `amount`、导出、导入匹配都受影响。

**建议**：PATCH 后对合并结果做整体校验：`code/name` 非空、`code` 唯一、`status ∈ options`、`price/quantity` 为有限数且 `>= 0`、`quantity` 按整数精度处理（或明确允许小数并统一导出精度）。

### P1-5 删除用户不转交其台账（孤儿数据）

```87:96:server/src/routes/users.js
  const tables = db.tables.filter((t) => t.ownerId === user.id);
  const rows = db.rows.filter((r) => r.createdBy === user.id || r.updatedBy === user.id);
  ...
  db.users = db.users.filter((u) => u.id !== req.params.id);
```

只转交 `tables/rows`，**`db.ledger` 没有处理**；同时把他人行的 `updatedBy` 改成管理员，丢失审计信息。实测删除后 `createdByName` 变成 `—`，`createdBy` 悬空，成员无法再编辑该台账（只有 admin 可以）。

**建议**：一并转交 `ledger.createdBy/updatedBy`（保留 `originalCreatedBy` 审计字段更佳）；不要改写 `updatedBy`，改为在展示层做"账号已删除"降级。

### P1-6 修改密码后旧 JWT 仍有效

JWT 仅含 `sub/role`，`requireAuth` 只校验签名与用户存在，未与密码版本绑定。实测改密后旧 token 仍能访问 `/auth/me`，最长 12 小时。对"共享电脑/令牌泄露"场景风险明显。

**建议**：用户表增加 `tokenVersion`（或 `passwordChangedAt`），签发时写入 claim，校验时比对；改密/改角色/管理员重置密码时自增，实现"一键下线"。

### P2-1 导入失败数被 30 条明细上限截断

`errors` 数组在 30 条后停止 push，但响应里 `failed: errors.length`（`routes/tables.js:417`、`routes/ledger.js:354`）。实测 40 行全失败 → `failed: 30`，前端"失败 30 条"与实际 40 条不符，且用户会误以为其余 10 行成功。

**建议**：独立 `failedCount` 计数器，`errors` 只作展示并新增 `errorsTruncated: true`；前端提示"仅展示前 30 条"。

### P2-2 伪造/损坏的 xlsx 返回 500 并泄露内部错误

`parseWorkbook` 未捕获 ExcelJS 异常，直接进全局错误处理；`err.status` 缺省 500 后把 `err.message` 原样返回给客户端。

```97:107:server/src/index.js
  const status = err.status || 500;
  ...
  res.status(status).json({ message: err.message || '服务器内部错误' });
```

**建议**：`try { await wb.xlsx.load(buffer) } catch { throw new HttpError(400, '文件无法解析，请确认是有效的 .xlsx') }`；5xx 一律返回固定文案，细节仅写日志。

### P2-3 字段枚举/格式校验缺失（select / date / status）

`validateRow` 只校验必填、数字、长度：

```100:115:server/src/store.js
  for (const col of table.columns) {
    const v = data[col.key];
    ...
    if (col.required && empty) errors.push(...);
    if (col.type === 'number' && !empty && typeof v !== 'number') errors.push(...);
    if ((col.type === 'text' || col.type === 'textarea') && ...) errors.push(...);
  }
```

下拉列不校验 `options`，日期列 `toDateOnly` 的 `/^\d{4}-\d{2}-\d{2}/` 会放行 `2026-13-99`，纯文本非法日期原样入库；台账 `status` 同样不受 `LEDGER_FIELDS.options` 约束。

**建议**：加 `select` 选项白名单、`date` 用严格 `YYYY-MM-DD` + 真实日历校验（dayjs `isValid`），台账状态做枚举校验；`HttpError` 汇总多条错误。

### P2-4 表格重命名无长度上限

创建限 30 字，PATCH 只判空与非重名（`routes/tables.js:112-120`）。实测可改 40 字，导致列表/导出/标签布局异常。

**建议**：抽 `assertTableName(name)` 供 POST/PATCH 共用。

### P2-5 `sync-ledger` 数字静默归零

```494:495:server/src/routes/tables.js
    const price = payload.price === undefined ? undefined : Number(payload.price) || 0;
    const quantity = payload.quantity === undefined ? undefined : Number(payload.quantity) || 0;
```

`abc`、`Infinity`、`-` 一律变 `0`；而表格录入与台账录入都会报 400，行为不一致。

**建议**：复用 `readLedgerPayload` 的严格解析，非法值记 `skipped` 并回传原因。

### P2-6 负数/小数与精度不一致

台账 `price=-10, quantity=-2` 可保存且 `amount=20`；`quantity=1.5` 与字段声明的 `precision: 0` 冲突（导出显示为整数格式）。工作台 `lowStock` 会把负库存算进预警。

**建议**：`price >= 0`、`quantity >= 0`，`quantity` 取整或明确允许小数并同步 `precision`；`stats` 排除负值异常数据。

### P2-7 台账 upsert 编号为空时静默新增

```309:311:server/src/routes/ledger.js
    if (mode === 'upsert') {
      const key = String(clean.code || '').toLowerCase();
      const found = key ? index.get(key) : null;
```

空编号不报错，落到新增分支生成 `AUTO-xxxxxx`。用户以为"按编号更新"，实际新增了脏数据。

**建议**：upsert 模式下 `code` 为空直接按行失败（"产品编号为空，无法匹配更新"）。

### P2-8 登录锁定按用户名 → 可锁死他人账号

连续 6 次错误即锁 5 分钟，正确密码也返回 429（实测）。攻击者可用已知用户名（如 `admin`）持续锁定，形成低成本 DoS；`attempts` Map 也没有过期清理，用户名喷洒会造成内存增长。

**建议**：`用户名 + IP` 作为键，成功登录只清该键；增加过期项定期清理；锁定期间可对同 IP 递增惩罚；或引入验证码。

3. **台账写入统一走一个 `validateLedgerEntry(merged)`**：code/name 非空、code 唯一、status 枚举、数字有限且非负（修 P1-4、P2-3、P2-6）。

### 6.2 短期（1 周，补质量护栏）

### 6.3 中期（架构演进）

14. **存储替换**：`db.js` 的接口（`getDb/loadDb/saveDb/flushDb`）可抽象为 repository；迁移到 SQLite（WAL 模式）即可获得事务、唯一索引（`ledger.code` 唯一约束）与并发安全，路由层几乎不改。

## 八、总体评价

- **做得好的地方**：领域拆分清晰（store/query/excel/routes 职责分明）；原子写 + 损坏备份 + 防抖落盘在"无数据库"前提下考虑周全；行级 `canEdit` 返回给前端做按钮置灰；导入"参数校验先于会话校验"、append 模式拦重复编号、成员不能覆盖他人数据等细节说明作者有安全意识；错误文案对用户友好；启动/停止脚本工程化程度高。
- **主要风险**：三处"部分更新"语义不一致（表格导入 vs 台账导入）、权限函数散落导致 `sync-ledger` 漏校验、数据生命周期（删用户/改密码）没有闭环。这些都属于**跨模块一致性问题**，单模块测试很难发现，也正是本次补充探针集中命中的区域。
- **建议节奏**：先修 P1（数据正确性与越权），再把探针转为回归用例锁住行为，最后做存储与校验框架的架构升级。
